## A Startup Enxuta — Ries

O livro mais influente sobre como construir sem desperdiçar.

### O Loop Fundamental: Construir → Medir → Aprender

Não é sobre velocidade de construção — é sobre velocidade de *aprendizado*.

```
Ideia → Construir (MVP mínimo) → Medir (métrica que importa) → Aprender (pivotar ou perseverar)
```

**O que a maioria erra:**
- Passa meses construindo um produto "completo" antes de qualquer validação
- Mede métricas de vaidade (pageviews, downloads) em vez de métricas acionáveis
- Confunde perseverança com teimosia: continuar sem evidência de PMF não é garra, é negação

### MVP — O Mínimo Produto Viável

O MVP não é uma versão ruim do produto. É o **experimento mais barato que testa a hipótese
de maior risco**.

- **Dropbox:** um vídeo de 3 minutos antes de qualquer código. Testou o problema, não a solução.
- **Zappos:** comprava sapatos em lojas físicas e os revendia online. Testou demanda antes de estoque.
- **Buffer:** uma landing page com botão de "planos e preços" antes de existir o produto.

**Pergunta antes de qualquer build:** "Qual é a suposição mais arriscada nessa ideia?
Qual é o experimento mais barato para testá-la em menos de 2 semanas?"

### Pivô vs. Perseverança

O pivô não é desistir. É mudar a estratégia mantendo a visão.

Tipos de pivô (os mais comuns):
- **Zoom-in:** uma feature vira o produto
- **Zoom-out:** o produto vira uma feature de algo maior
- **Segmento de cliente:** mesmo produto, cliente diferente
- **Necessidade do cliente:** mesmo cliente, problema diferente

**Regra de Ries:** se você está executando o plano mas os números não melhoram, talvez seja hora de pivotar. Se os números melhoram mas mais devagar do que você precisa, otimize. Se os números não se movem há 2-3 ciclos de aprendizado, o que você está aprendendo?

## Apaixone-se pelo Problema, Não pela Solução

O princípio mais contraintuitivo para fundadores técnicos: a solução que você ama não é
o negócio. O problema que o cliente *precisa* resolver é.

**O processo correto:**
1. Encontre um problema que seja **frequente, urgente e que as pessoas paguem para resolver**
2. Valide que o problema é real falando com 20-50 potenciais usuários (entrevistas, não pesquisas)
3. *Só então* comece a pensar em solução

**Perguntas de entrevista de problema (sem vender):**
- "Conte-me como você faz [processo] hoje."
- "Qual é a parte mais difícil disso?"
- "Com que frequência isso acontece?"
- "O que você já tentou para resolver?"
- "Quanto isso custa (tempo/dinheiro) quando dá errado?"

Se o problema não aparecer espontaneamente, talvez não seja um problema real — é um problema que você *imagina* que eles têm.

## Sprint — Jake Knapp (Google Ventures)

O Sprint de 5 dias é um protocolo para resolver grandes questões de design e estratégia
em uma semana, em vez de meses.

### A Estrutura

| Dia | O que acontece |
|-----|---------------|
| Segunda | Mapear o problema, escolher o alvo |
| Terça | Explorar soluções individualmente |
| Quarta | Decidir a solução a testar |
| Quinta | Construir protótipo realista |
| Sexta | Testar com 5 usuários reais |

**Regra de ouro:** 5 usuários são suficientes para identificar 85% dos problemas de usabilidade. Não é pesquisa estatística — é aprendizado qualitativo rápido.

**Quando usar o Sprint:**
- Decisão de produto de alto risco, alto custo de erro
- Time sem alinhamento sobre a direção
- Problema complexo que parece não ter solução
- Antes de iniciar um projeto grande

## Scrum — Jeff Sutherland

Scrum é o framework mais adotado para execução ágil. Mas a maioria o usa errado.

### O que realmente importa no Scrum

**1. O Backlog priorizado é lei.** O item mais importante está no topo. Tudo mais é detalhado só quando sobe para os próximos sprints — detalhar o que está no fundo é desperdício.

**2. Sprint = compromisso, não estimativa.** O time decide o que cabe no sprint e se compromete. Compromisso cria accountability. Estimativa cria desculpa.

**3. A Daily não é relatório de status.** São três perguntas: O que fiz ontem que ajudou o time a atingir a meta do sprint? O que farei hoje? Há algum impedimento?

**4. Retrospectiva é o motor de melhoria.** Uma coisa a mudar por sprint, implementada imediatamente. Retrospectiva sem ação é só reclamação organizada.

### A Velocidade Dobrada

O título do livro (fazer o dobro na metade do tempo) não é hipérbole — é o resultado documentado de times que removem desperdícios:
- Reuniões sem decisão
- Multitarefa que mata foco
- Espera por aprovação
- Retrabalho por falta de especificação

## OKRs — John Doerr

O sistema que Intel, Google e Bono Vox usaram para transformar ambição em execução.

### A Estrutura

**Objetivo:** o que você quer alcançar — qualitativo, inspirador, sem número.
**Key Results:** como você saberá que chegou lá — quantitativos, binários ou escalares.

Exemplo:
```
Objetivo: Nos tornar a agência de referência em tráfego pago no interior de SP
KR1: Fechar 3 novos clientes de serviço completo até 30 de setembro
KR2: ROAS médio da carteira ≥ 4x em agosto e setembro
KR3: NPS de clientes ativos ≥ 70
```

### Regras que a maioria ignora

- **OKRs não são lista de tarefas.** São apostas. Se você está 100% confiante de atingir todos, não são ambiciosos o suficiente.
- **60-70% de atingimento é sucesso.** OKRs ambiciosos que chegam a 70% valem mais que OKRs fáceis chegando a 100%.
- **Trimestrais + Anuais.** Trimestrais para velocidade, anuais para direção.
- **Não atrelados a bônus.** Quando OKR = bônus, as pessoas criam KRs fáceis. Separe.
- **Máximo 5 OKRs, 3-5 KRs cada.** O que é prioridade de todo mundo não é prioridade de ninguém.

## A Startup de $100 — Guillebeau

O contra-argumento para a narrativa de que você precisa de investimento, escritório e
equipe para construir um negócio.

**Os padrões dos 1.500 fundadores estudados:**
- Mediamente 600-1.000 dólares para começar
- Skill + paixão + o que as pessoas pagam = negócio viável
- A maioria dos negócios lucrativos começa com um único cliente, obtido manualmente
- Nenhum deles esperou pelas condições perfeitas

**A equação simples:**
```
O que você sabe fazer bem + O que as pessoas precisam urgentemente + Como receber pelo valor = Negócio
```

**O teste de 1 semana:** antes de construir qualquer coisa, tente vender. Não "valide o interesse" — tente receber dinheiro. Se alguém pagar, você tem um negócio. Se não, você tem uma hipótese.

## A Regra É Não Ter Regras — Netflix

Reed Hastings e Erin Meyer documentaram a cultura que construiu a Netflix.

**Os três pilares:**

**1. Densidade de Talento acima de tudo.** Um time pequeno de pessoas extraordinárias supera um time grande de pessoas boas. A primeira demissão que libera uma posição para um jogador A+ é um investimento, não uma perda.

**2. Sinceridade radical com feedback.** A pergunta padrão na Netflix não é "como foi?" mas "o que eu poderia ter feito melhor?". O feedback dado com respeito e em tempo real é um ato de cuidado — retê-lo é covardia disfarçada de gentileza.

**3. Contexto, não controle.** Quanto mais você explica *por que* (contexto, estratégia, princípios), menos regras você precisa. Pessoas inteligentes com contexto suficiente tomam decisões melhores do que processos que tentam prever todos os cenários.

**O teste do Keeper:** "Se essa pessoa me pedisse demissão hoje, eu lutaria para mantê-la?" Se a resposta for não, a conversa honesta é agora — não na próxima avaliação.

## Zero to One — Peter Thiel

*Fonte: blakemasters.com/peter-thiels-cs183-startup (notas originais gratuitas da aula CS183 Stanford)*

**A tese central:** Copiar o que existe é ir de 1 para n. Criar algo genuinamente novo é ir de 0 para 1. Apenas o segundo cria valor real e duradouro. A competição é para perdedores — monopólios são para vencedores.

**A pergunta mais importante do livro:**
*"O que você acredita que é verdade e que quase ninguém concorda com você?"*
Fundadores que constroem empresas de 0 para 1 começam com uma crença contrária ao consenso que se prova correta.

**Por que monopólios são a meta:**
- Empresas competitivas lutam pela sobrevivência com margens mínimas — não têm capital para inovar
- Monopólios têm margens para investir em longo prazo, cuidar de funcionários, criar produtos melhores
- Google domina busca, captura enorme valor, e usa isso para financiar outros projetos
- A competição perfeita é ótima para consumidores e ruim para quem constrói

**Os 4 atributos de um negócio de 0 para 1:**
1. **Tecnologia proprietária** — pelo menos 10x melhor que a alternativa mais próxima em alguma dimensão
2. **Efeito de rede** — fica mais valioso conforme mais pessoas usam (Facebook, WhatsApp, LinkedIn)
3. **Economias de escala** — custo marginal cai conforme cresce (software é o exemplo puro)
4. **Branding** — identidade forte que não pode ser copiada (Apple)

**A lei do poder em startups:**
Thiel (como investidor da YC/Founders Fund) descobriu que em qualquer portfólio, um único investimento supera todo o resto combinado. A maioria dos retornos vem de um número muito pequeno de apostas. Implicação para founders: pense em qual é o seu equivalente — qual aposta vai superar tudo o que você está fazendo?

**Segredos:**
Thiel usa "segredo" para descrever verdades que existem mas que a maioria ignora ou não procura. "Toda grande empresa é construída em torno de um segredo que o mundo não conhece ainda." Para encontrar segredos: onde a convenção para as pessoas de pensar? O que é tabu questionar na sua indústria?

## The Mom Test — Rob Fitzpatrick

*Fonte: momtestbook.com*

**O problema que o livro resolve:** Perguntar para pessoas se elas gostam da sua ideia é inútil — elas vão mentir para não magoar você. Incluindo sua mãe.

**As 3 regras do Mom Test:**
1. Fale sobre a vida deles, não sobre a sua ideia
2. Pergunte sobre o passado específico, não opiniões ou intenções futuras
3. Ouça mais, fale menos

**O que nunca perguntar:**
- "Você usaria isso?" (resposta inútil — intenção futura não é comportamento)
- "Você pagaria por isso?" (hipotético, inútil)
- "Você acha uma boa ideia?" (mede simpatia, não demanda real)

**O que perguntar:**
- "Me conta como você lida com [problema] hoje"
- "Qual foi a última vez que você [enfrentou o problema]? O que aconteceu?"
- "Você já tentou resolver isso? O que não funcionou?"
- "O que você mais gasta de tempo fazendo nessa área?"
- "Quanto isso custa hoje resolver do jeito que você resolve?"

**O sinal mais valioso:** quando alguém já está pagando por uma solução ruim para um problema, ou quando "fazem um workaround vergonhoso" para contornar o problema — esses são os melhores clientes potenciais.

**Aplicação para NexMint:**
Antes de qualquer reunião de escopo (Mario, CAP Jr., agências), o objetivo não é apresentar — é descobrir. Cada conversa deve terminar com você sabendo mais sobre o problema do que quando começou, e o cliente sem ter ouvido nenhum pitch.

## Shape Up — Ryan Singer (Basecamp)

*Fonte: 100% gratuito em basecamp.com/shapeup*

**A tese:** Metodologias como Scrum com sprints de 2 semanas criam ciclos de urgência artificial e backlog infinito. A Basecamp criou um processo diferente que funciona melhor para produtos maduros.

**Os 3 modos:**

**1. Shaping (moldar)** — trabalho de descoberta e design feito *antes* de colocar no ciclo de desenvolvimento. O problema é analisado, a solução é esboçada com "fat marker sketches" (não wireframes detalhados), e o "apetite" (tempo que queremos gastar, não estimativa) é definido.

**2. Betting (apostar)** — a cada 6 semanas, há uma "betting table" onde as lideranças escolhem quais shaped projects entram no próximo ciclo. Não há backlog — o que não é escolhido simplesmente some, a menos que alguém defenda novamente.

**3. Building (construir)** — times pequenos (1-2 devs + 1 designer) têm 6 semanas e autonomia total para entregar. Nenhuma extensão — se não terminar no prazo, o projeto é cancelado.

**O conceito de "apetite" vs. estimativa:**
Em vez de "quanto tempo vai levar?", a Basecamp pergunta "quanto tempo queremos gastar nisso?" É uma decisão de negócio, não uma previsão técnica. Um apetite de 2 semanas define o escopo que cabe em 2 semanas — não tenta adivinhar se vai demorar 2 semanas.

**Hill Charts:**
Em vez de % de conclusão (enganoso), times rastreiam progresso em uma colina: subindo = descoberta (incerteza diminuindo), descendo = execução (trabalho concreto). Um projeto preso na subida indica problema de design não resolvido.

## Inspired — Marty Cagan (SVPG)

*Fonte: svpg.com/articles — dezenas de artigos gratuitos que formam a base do livro*

**A distinção central:** a maioria das empresas opera como "feature factory" — o business decide o que construir, o produto escreve specs, o design desenha, o dev implementa. Cagan argumenta que isso é o modelo errado.

**O modelo de produto empoderado:**
- Times de produto (trio: PM + designer + engenheiro) são responsáveis pelo **problema**, não pela **solução**
- O business define os objetivos e restrições — o time descobre como atingi-los
- A descoberta (discovery) e a entrega (delivery) acontecem em paralelo, não em sequência

**Os 4 riscos de produto que o discovery deve resolver:**
1. **Risco de valor** — o cliente vai querer isso?
2. **Risco de usabilidade** — ele consegue usar?
3. **Risco de viabilidade** — conseguimos construir? (técnico, legal, de negócio)
4. **Risco de viabilidade de negócio** — funciona para a empresa?

**Product-Market Fit (PMF):**
Cagan define PMF não como um evento, mas como uma busca. O sinal mais confiável: retenção. Se as pessoas continuam usando e pagando depois de 30-60-90 dias sem intervenção manual sua, você tem algo. Se precisar "empurrar" cada renovação, você não tem PMF ainda.

**O "produto" para a NexMint:**
O MintBoard hoje está em fase de descoberta de PMF. A pergunta não é "o que construir a seguir?" mas "quais clientes retêm e por quê?" — aqueles são os clientes cujo problema o MintBoard resolve de verdade. Eles são o molde do produto.

## Crossing the Chasm — Geoffrey Moore

*Fonte: Four Minute Books; artigos em a16z.com*

**A tese:** A maioria das startups de tecnologia morre não porque o produto é ruim, mas porque falham em atravessar o "abismo" entre os early adopters e o mercado mainstream.

**A curva de adoção de tecnologia:**

```
Innovators (2.5%) → Early Adopters (13.5%) → [ABISMO] → Early Majority (34%) → Late Majority (34%) → Laggards (16%)
```

**O abismo:**
Early adopters compram visão e toleram bugs. A maioria inicial (mainstream) quer referência comprovada, integração com o que já usam, e suporte confiável. São psicologias completamente diferentes.

**A estratégia "beachhead" (cabeça de praia):**
Em vez de tentar conquistar o mercado todo, Moore recomenda dominar um segmento específico completamente primeiro — se tornar a referência indiscutível para aquele nicho — e só então expandir.

**Para o MintBoard:**
Hoje o MintBoard está com early adopters (primeiros beta users). Para atravessar o abismo para agências digitais em geral, precisa de: casos de sucesso documentados, integrações com ferramentas que as agências já usam, e suporte que não depende dos fundadores pessoalmente.

**A pergunta do beachhead:** "Qual é o segmento menor e mais específico de agências onde o MintBoard pode ser a escolha óbvia e indiscutível?" Dominar esse primeiro, depois expandir.
